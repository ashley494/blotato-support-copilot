# Real-ticket replay

Run date: 2026-11-10. Rerun with `npm test`; the numbers and tables between the replay markers below are rewritten by `test/replay.test.ts` on every run. The text outside the markers is written by hand.

## What this measures

For each case, the copilot gets `{status, message: customerText}` and `explainError` ranks its explanations.

- **Top-1 hit:** the expected rule is the first result.
- **Top-3 hit:** the expected rule is in the first three.
- **Gate pass:** for top-1 hits, the rule's `customerReply` is scored by `gateReply` with the case as the issue. Current gate: 10 yes/no checks, 1 point each, and a built-in reply must meet all 10. Full rubric: [scoring.md](scoring.md).

- **Real cases: 48** in `test/fixtures/real-tickets.json`, one per individual report in `docs/ticket-evidence.md`. 32 are in the window (2025-11-09 to 2026-11-09) and 16 are older.
- **Re-read from the source:** all 11 GitHub issues on Blotato-Inc/n8n-nodes-blotato, n8n-io/n8n #24021 and #24223, the 3 customer-repo PRs, 4 n8n forum threads and all 3 Make threads.
- **Not re-read:** 5 n8n threads (the forum rate-limited the fetch), Trustpilot and G2. Those cases are paraphrased from the evidence doc's summaries.
- **Two cases not counted in the evidence doc:** issue #6 (rt-24) and post 1 of n8n thread 172669 (rt-20). The doc read both sources but did not list these reports.
- **Same author, different problems:**
  - One Make user wrote the three Make threads (rt-27, rt-28, rt-29), each about a different problem.
  - One n8n thread, 130711, gave two cases (rt-36, rt-37).
  - Four cases (rt-31 to rt-34) come from one agency account in Blotato's own blog post. They are the vendor's words, not the customer's.
  - Counting those, there are about 43 distinct reporters.
- **Pairings:** the evidence doc lists Trustpilot summaries and reviewers in the same order. Each summary is paired with the reviewer in the same position, which is an assumption.
- **Easier cases:**
  - rt-30's text already names the root cause (a temporary preview link), because the doc's summary does.
  - rt-29 leaves out the error text, because the customer only posted a screenshot.
- **New rules needed:** 15 real cases have `newRule: true`. No rule existed for them, so they could not hit at baseline. Of the 33 cases that had an existing rule, the baseline got **15 of 33 (45%)** at top-1.

### Held-out sets

- **Held-out A (8 cases)**, `test/fixtures/held-out-tickets.json`. I wrote these before changing any rule. **This set leaked.** I looked at some of them while writing the new patterns, so 8/8 is not an independent result.
- **Held-out B, blind (14 cases)**, `test/fixtures/held-out-blind.json`. A separate agent wrote these after the rules were tuned. It saw only a one-line description of each issue id, never the rules or the real tickets. I did not change any rule after seeing its results. **This set gives the honest generalisation number.** Its baseline was computed by running the pre-change `explain.ts` on the same cases. Gate scores for those baseline hits come from the current gate.

## Reading the numbers

- **Real set, 100% after:** this is training accuracy. The rules were tuned while looking at these 48 cases, so they will always look good here. It proves that every real report now has a rule and a reply that passes the gate, and nothing more.
- **Top-3 equals top-1 in every run.** On these short texts, two rules rarely fire together, so top-3 adds no information here.
- **Blind set: 4/14 (29%) before, 10/14 (71%) after.** This is the number to quote. Keyword rules still break on paraphrase (see the remaining misses).
- **Billing and refunds:** 12 real cases (9 billing, 3 lockout) go to `billing-trial-api-key` or `login-locked-out`. Both have `escalate: true`, both replies hand off to a person, and neither promises a refund. These cases count as correct handling. The copilot routes them to a human and does not try to resolve them.

## What changed in `src/explain.ts`

### New rules (8)

| Rule | Escalates? | What it covers |
|---|---|---|
| `login-locked-out` | Yes | Can't sign in, locked out, login failing. Ordered before billing, because these customers also mention paying. |
| `n8n-node-bug` | Yes | The node crashes ("Cannot read properties of undefined"), takes the success branch on an error, or won't let a value be chosen. The reply collects n8n and node versions and suggests the HTTP Request node as a stopgap. When the text mentions scheduling, it adds a hint about the ISO 8601 date format. |
| `upload-201-created` | No | Client code treats 201 Created as a failure. Ordered after `silent-success`. |
| `tiktok-public-url` | Yes | The post's publicUrl points at the profile instead of the post. |
| `linkedin-nonexistent-version` | Yes | LinkedIn NONEXISTENT_VERSION, or "version not active / deprecated". |
| `find-account-ids` | No | Where to get accountId and pageId, or typing ids by hand. Points to `/v2/users/me/accounts` and `/subaccounts`. |
| `ai-video-credits-quality` | Yes, to product | Credits, AI video quality, template changes. Ordered late so real errors win. |
| `post-analytics` | No | Analytics, impressions, stats, likes or views. Links the help entry on analytics via the API. The reply mentions Sheets only when the customer does. |

### Broadened rules

- **`billing-trial-api-key`:** catches any money event: charge, bill, refund, money back, past due, double charge, a cancellation that failed, a payment or purchase that didn't apply or that started a subscription, or a dollar amount. (Its reply was rewritten later on 2026-11-10 after a support-lead review: it explains the key-ends-trial rule, how to cancel, and hands the charge to the billing team with the receipt details.)
- **`n8n-node-install`:** catches checksum or package-integrity errors, "node type", "legacy version", a single "question mark", and "find / install / add / update the Blotato node". Two fixes were added from re-reading the tickets:
  - The package name is `@blotato/n8n-nodes-blotato`. The `.blotato` suffix is the node type (n8n #24021).
  - A preview-package template needs the preview package (issue #10).
- **`media-90009`:** catches "Failed to read media metadata" (Blotato sends it as a 500, so it used to land on server-9999), "can't read / fetch / download the file", and Google Drive, Dropbox, preview, temporary, signed or proxy links. It also catches a failure word next to "media" or next to a media URL. The fix now covers temporary and proxy links and hosts that work only some of the time.
- **`unsupported-media`:** moved above `media-90009`. It now catches other wordings of "format not supported", "Could not upload media to storage", and .mov / .avi / .mkv / .webm / .heic. The reply mentions converting .mov.
- **`upload-in-progress`:** also catches "it showed an error, but the file uploaded anyway", when a media or upload word is present.
- **`silent-success`:** allows more words between "success / green / completed" and "nothing / hasn't ... posted".
- **`n8n-server-url`:** catches an n8n credential or server field ending in `/v2` (but not `/v2/...`), n8n's longer "resource you are requesting could not be found", and `/v2/v2`.
- **`auth-401`:** catches "key invalid / rejected / refused / not accepted" without a status code.

No rule pastes a ticket's exact wording, with one exception: an error string a customer would paste as-is (NONEXISTENT_VERSION, "Failed to read media metadata"). That is the same approach as the existing rules for 90009 and "already in progress".

## Remaining misses (blind set, 4 of 14)

| Case | Expected | Got | Plain reason |
|---|---|---|---|
| hb-07 | upload-in-progress | unknown | The customer says the image is "sitting in blotato just fine". The "it worked anyway" pattern only knows words like still, anyway, there, loaded and uploaded. |
| hb-08 | tiktok-url-ownership | unknown | The customer says "verifying that I own the URL". The rule needs "URL ownership", "ownership verification" or "verify ... domain". |
| hb-11 | published-immediately | unknown | The customer says "went live the second I hit run". The rule needs posted, published or went out next to immediately, right away or too early. |
| hb-14 | stuck-in-progress | unknown | The customer writes "in progress" with a space. The rule needs "in-progress", "stuck", "still processing" or "pending forever". |

All four go to `unknown`, which escalates to engineering. The customer still gets a human, but not the fix they could have applied themselves. I left these four unfixed on purpose: fixing them now would turn the blind set into a training set. They are the next rules to widen, and the check after that needs a new blind set.

### Other weaknesses found

- **hb-02:** "two identical Blotato charges on my credit card" ranks correctly at top-1. But "credit" also fires `ai-video-credits-quality` at second place. The credits pattern should exclude "credit card".
- **Order dependence:** the top result depends on rule order. Billing sits before `plan-403`, whose pattern (`subscription|paid plan|trial`) is broad and used to take most billing complaints.
- **One billing reply for everything:** the billing reply is shared by trial charges, double charges and failed cancels. It is correct to escalate, but for a double charge the trial explanation is noise.
- **Assumptions in the new rules:**
  - The LinkedIn version cause is an assumption from the evidence doc.
  - The `post-analytics` reply rests on the help entry and the Blotato MCP's post analytics tools. The REST endpoint was not checked live.
